# literature-to-protocols

A **Literature-to-Protocols** toolkit repository for chemical experimental literature.  
This project combines **knowledge graphs (KGs)** and **large language models (LLMs)** to extract experiment-related information from scientific papers and generate structured, reviewable, and traceable protocol templates for experiment design reference, result organization, and further exploration of conversion into laboratory platform code.

> This repository is currently better suited as a **paper method implementation + example showcase repository**.  
> Some directories are mainly intended to demonstrate prompt design, generated examples, entity-level comparison, and evaluation logic, so not all contents are meant to support one-click execution of complete baseline comparison experiments.

---

## Overview

Experimental procedures in scientific papers are usually scattered across free-form text, which makes them difficult to reproduce, compare, and automate.  
The goals of this project are:

* Extract experiment-related entities, conditions, operations, and relations from papers
* Build paper-level knowledge graphs
* Generate structured protocols through templated prompting and graph-based retrieval
* Evaluate the generated results in terms of factuality, text quality, and questionnaire-based practical usability

From the perspective of the paper, the output of this project is a **protocol intermediate representation suitable for human review and downstream conversion**, rather than a final execution language for a specific robotic platform.

---

## Features

* **Knowledge-graph-driven**: Organizes experimental information in papers into structured graphs for easier retrieval and traceability
* **LLM-assisted generation**: Combines prompt templates and graph-based QA to generate structured experimental protocols
* **Designed for literature-based experimental workflows**: Suitable for parsing experimental literature in chemistry and materials science
* **Supports case analysis**: Includes generated examples, top-k retrieval comparisons, entity difference discussions, and more
* **Supports downstream conversion exploration**: Provides examples of converting protocols into laboratory platform code

## What Can Be Directly Run in This Repository

The **main entry points** of the current repository are:

* `graph_search.py`: main program entry
* `graph_utils/`: core code for knowledge graph construction, retrieval, and generation
* `graph_utils/chatgpt/config/config.yaml`: configuration for models, APIs, proxies, etc.
* `graph_utils/chatgpt/config/prompts_config.json`: prompt configuration file
* `template/FT/ft.md`: template for the FT scenario
* `origin_paper/more_paper/`: directory for input papers to be parsed
* `papersavings/`: output directory for generated results

In most cases, once the environment, model parameters, Neo4j, and the PDF parsing service are properly configured, you can start the main workflow by running:

```bash
python graph_search.py
````

## Installation

### 1. Main Environment

```bash
conda env create -f freeze.yml
conda activate ftpack
```

After installation, first edit the model configuration file:

```bash
vi graph_utils/chatgpt/config/config.yaml
```

You need to fill in your own:

* API Key
* base URL
* proxy (if needed)

---

### 2. Neo4j Knowledge Graph Database

This project uses Neo4j for knowledge graph storage and retrieval.
Please install and start Neo4j first (version 5.10+ is recommended).

Then modify the database connection parameters. You may refer to the following example in the repository:

```python
# Example path: graph_utils/graph_generate_bak.py
os.environ["NEO4J_USERNAME"] = "neo4j"
os.environ["NEO4J_PASSWORD"] = "password"
```

Please replace them with your own username and password.

---

### 3. PDF Parsing Service

This project relies on `marker_server` for PDF parsing.

```bash
conda create -n marker python=3.10.0
conda activate marker

pip install marker-pdf
pip install -U uvicorn fastapi python-multipart
```

Start the parsing service with:

```bash
marker_server --port 2675
```

After startup, it can be accessed through the local interface.

## Repository Structure

### Main Workflow Related

#### `graph_search.py`

Main entry point of the project.
Responsible for coordinating paper parsing, knowledge graph retrieval, section-wise generation, and result saving.

#### `graph_utils/`

Core code directory, including modules for knowledge graph construction, file loading, example loading, and review, such as:

* `graph_generate_bak.py`
* `graph_generate_optimized.py`
* `load_example.py`
* `load_files.py`
* `review.py`

#### `graph_utils/chatgpt/config/config.yaml`

Configuration file for runtime parameters, including API, base URL, proxy, and other model-related settings.

#### `graph_utils/chatgpt/config/prompts_config.json`

Main prompt configuration file.
Prompts for question decomposition, section generation, content filtering, table-of-contents generation, and other tasks are centrally maintained here.

#### `change_prompt.py`

A helper script for batch prompt replacement.
If you need to replace templates, switch topics, or update prompts in a unified way, this is a good place to start.

---

### Template and Evaluation Related

#### `template/`

Template directory for the Fischer–Tropsch (FT) scenario.

It mainly includes:

* `template/FT/ft.md`: the template used in the FT scenario, also our **L2 prompt template**
* `template/FT/evaluation/all_paper_en.md`: one of the important prompt files used for questionnaire-based evaluation in the paper

#### Notes on `evaluation`

The contents in `evaluation` are mainly intended to demonstrate:

* evaluation prompt design
* question design
* evaluation code logic
* how the evaluation methodology in the paper is implemented

Please note:
Since the repository **does not provide all baselines together with the full supporting evaluation environment required for direct reproduction**, the evaluation code here **should not be treated as a complete out-of-the-box baseline comparison system**. It is more suitable for reading prompts and understanding the code logic.

---

### Data and Examples

#### `origin_paper/`

Directory for original input papers.
The main workflow reads and parses paper contents from here.

#### `origin_paper/more_paper/`

Directory for papers to be processed.

#### `papersavings/`

Output directory for the protocol templates generated by our method.
The repository already contains a series of `Paper_*.md` files, which can be used as example outputs.

#### `originpaper`

Prototype content extracted and organized from the original papers, intended for comparison with the final generated templates.

#### `example`

A series of comparison examples used to show the differences between different generation methods and organization styles.

#### `entities_discussion`

Used to discuss the differences in entities generated by different methods, with a focus on entity extraction results rather than the full workflow.

#### `papersavings-topk`

A directory for retrieval-setting analysis from the paper.
It mainly shows how the final generated templates differ under **different Top-K retrieval settings**.

#### `protocols2commands`

An example of converting generated protocols into laboratory platform code.
Since this direction is still immature and the laboratory platform itself is in Chinese, this part is currently **entirely in Chinese** and is better viewed as a proof-of-concept example.

## Model Configuration Notes

If you want to change the LLMs used in the project, you should mainly look at the configurations for graph generation, reasoning, and lightweight calls.
For example, the current project commonly separates them as follows:

* Main generation model: used for protocol section generation and integration
* Reasoning model: used for question decomposition and complex retrieval reasoning
* Lightweight model: used for partial extraction, filtering, and auxiliary tasks

Please refer to the code and `config.yaml` for the actual parameter settings.

## Usage Tips

Before the first run, it is recommended to check:

1. Whether the Neo4j service is running
2. Whether the API configuration in `config.yaml` is correct
3. Whether `marker_server` has been started
4. Whether the papers to be processed have been placed in `origin_paper/more_paper/`

If PDF parsing fails, you can try upgrading:

```bash
pip install marker-pdf --upgrade
```

If you need a proxy to access model services, you can configure `proxy` in `config.yaml`.

## Project Scope and Limitations

This repository is better understood as a **research-oriented method repository**, rather than a complete industrial-grade product.

### What It Is Currently Suitable For

* Extracting experimental workflow information from chemistry/materials science papers
* Building paper-level knowledge graphs
* Generating structured experimental protocol templates
* Analyzing the impact of different prompts and retrieval settings on generation quality
* Exploring possible paths for converting protocols into laboratory platform code
